# 传输层生产就绪修复（阶段五 C）说明文档

**阶段**：五 C（transport 生产就绪修复）
**适用范围**：`umcp_core.transport` 子包（HTTP API、JWT 认证、WebSocket 推送、仓储接口、lifespan 资源管理）以及 `core/task`、`core/deal`、`events` 的事件发布联动
**文档定位**：面向核心库维护者与部署工程师，完整说明阶段五 B 审查中发现的 4 个阻断级生产就绪问题的修复设计、关键实现、使用方法与测试覆盖。

---

## 一、概述

### 1.1 阶段目标

阶段五 B 在 in-memory 模式下交付了 HTTP API + JWT 认证 + WebSocket 推送（447 passed），但最终整体审查发现 4 个阻断级生产就绪问题。阶段五 C 的目标是逐项修复这 4 个阻断点，使 transport 层在 PG 模式下可用、token 吊销完整、WS 推送链路对真实业务事件生效、应用关闭时释放资源。

### 1.2 解决的问题

| # | 阻断点 | 根因 | 影响 |
|---|--------|------|------|
| 1 | logout/refresh token 吊销不完整 | logout 只吊销 access `jti`，refresh 仍可换新；refresh 端点不吊销旧 token | 登出形同虚设，refresh token 可无限重放 |
| 2 | list 端点穿透仓储私有属性 | router 用 `getattr(repo, "_tasks", {})` 直接读私有字典，PG 仓储无此属性 | PG 模式下 list 端点静默返回空 |
| 3 | lifespan 未释放 PG 资源 | shutdown 钩子不调用 `server.stop()` / `server.dispose()` | PG 连接池泄漏，进程退出阻塞 |
| 4 | WS 推送链路对真实事件不生效 | `Task._emit` payload 缺 `demander_id`，`Deal` 完全不发事件 | WS 桥接函数 `_extract_user_ids` 匹配不到 user_id，白名单内 task/deal 事件永不触发 |

### 1.3 核心设计

四个阻断点对应四组独立修复，互不耦合：

1. **Token 关联策略**：签发时在 access token 的 claims 中嵌入 `refresh_jti` 字段（引用同一 refresh token 的 jti）。logout 解码 access 即可拿到 `refresh_jti` 一并吊销；refresh 端点签发新对前先吊销旧 refresh jti（token 轮换）。
2. **List 查询接口**：仓储接口新增 `list_all() -> list[T]` 抽象方法，返回全量领域对象；router 层按 status/domain_tag 等参数过滤。接口简单，PG 实现为 `SELECT *`，避免穿透私有属性。
3. **Lifespan 资源释放**：`transport/app.py` 的 lifespan shutdown 分支在现有 WS 清理之后追加 `server.stop()` 与 `server.dispose()`。`dispose()` 内部有 `hasattr(self, "_postgres_bundle")` 守卫，in-memory 模式下是 no-op。
4. **WS 推送链路**：`Task._emit` payload 补 `demander_id`（始终）+ `supplier_id`（assign 时）；`Deal` 添加 `event_bus` 机制，状态变更发布 `DEAL_*` 事件；router 创建/激活/完成/争议/取消/解决时绑定 `event_bus` 并发布 `DEAL_CREATED`。

| 设计决策 | 选项 | 是否采纳 | 理由 |
|---------|------|---------|------|
| Token 关联 | access 嵌入 refresh_jti | 是 | 无需客户端额外传参，无需服务端维护映射 |
| List 查询 | 仓储返回全量 + router 过滤 | 是 | 接口简单，PG 实现为 `SELECT *`，小数据量场景足够 |
| Deal activate 事件 | 复用 `DEAL_PAID` | 是 | 语义为"已付款进入履约"，不新增枚举 |
| DEAL_CREATED 发布位置 | router 层发布 | 是 | Deal 构造时无 event_bus，由 router 在 `save` 后显式发布 |

## 三、核心设计

### 3.1 Token 吊销完整性

#### 3.1.1 access token 嵌入 refresh_jti

`JwtService.issue`（`transport/auth.py:35-70`）改造后先生成 `refresh_jti`，既作为 refresh token 的 `jti`，也作为 access token 的 `refresh_jti` 字段：

```python
refresh_jti = uuid.uuid4().hex
access_payload = {
    **base_claims,
    "iat": now,
    "exp": now + timedelta(seconds=self._access_ttl),
    "jti": uuid.uuid4().hex,          # access 自己的 jti
    "type": "access",
    "refresh_jti": refresh_jti,        # 嵌入 refresh 的 jti
}
refresh_payload = {
    **base_claims,
    "iat": now,
    "exp": now + timedelta(seconds=self._refresh_ttl),
    "jti": refresh_jti,                # 与 access.refresh_jti 一致
    "type": "refresh",
}
```

**access token claims 变化：**

```
现有：{sub, name, roles, active_role, iat, exp, jti, type:"access"}
新增：{..., refresh_jti: "<refresh_token 的 jti>"}
```

#### 3.1.2 logout 双吊销

`logout` 端点（`transport/routers/auth.py:87-112`）解码 access token 后取两个字段分别吊销：

```python
payload = jwt_service.decode(token)
# 吊销 access token
access_jti = payload.get("jti")
if access_jti:
    jwt_service.revoke(access_jti)
# 吊销关联的 refresh token（access 中嵌入的 refresh_jti）
refresh_jti = payload.get("refresh_jti")
if refresh_jti:
    jwt_service.revoke(refresh_jti)
```

无需客户端额外传 refresh token，单次 logout 即可让 access 与 refresh 同时进入黑名单。

#### 3.1.3 refresh 端点 token 轮换

`refresh` 端点（`transport/routers/auth.py:61-84`）在签发新对之前吊销旧 refresh jti，防止旧 refresh token 被重放：

```python
# 吊销旧 refresh token（token 轮换，防止重放）
old_jti = payload.get("jti")
if old_jti:
    jwt_service.revoke(old_jti)

# 重建 User 并签发新 token 对
user = user_from_claims(payload)
tokens = jwt_service.issue(user)
```

旧 access token 的 jti 不主动吊销（自然过期），因为客户端会用新 access 替换。新签发的 access token 仍嵌入新 refresh 的 jti（`issue` 保证）。

#### 3.1.4 token 吊销数据流

```
登录 login
  │
  └─ JwtService.issue(user)
         │
         ├─ access.jti = uuid4()           (独立)
         ├─ access.refresh_jti = uuid4()   ─┐
         └─ refresh.jti = uuid4()          ◄┘ (复用)
                              │
                              ▼
                客户端持有 {access, refresh}
                              │
        ┌─────────────────────┴─────────────────────┐
        │                                           │
        ▼                                           ▼
   logout 路径                                refresh 路径
   ├─ decode(access)                          ├─ decode(refresh)
   ├─ revoke(access.jti)                      ├─ 校验未吊销
   └─ revoke(access.refresh_jti)              ├─ revoke(refresh.jti)   ← 旧 token 轮换
                                              └─ issue(user) → 新对
                                                    │
                                                    └─ 新 access.refresh_jti = 新 refresh.jti
```

### 3.2 List 端点仓储接口

#### 3.2.1 接口扩展

在 `repositories/interfaces.py` 的 3 个仓储接口各加 `list_all()` 抽象方法（`interfaces.py:45-48`、`74-77`、`99-102`）：

```python

    ...

    """返回所有资源（router 层负责过滤）。"""
    ...

# DealRepository
@abstractmethod

    """返回所有交易（router 层负责过滤）。"""
    ...
```

#### 3.2.2 InMemory 实现

InMemory 仓储在锁保护下返回内部字典 values 的副本（`in_memory.py:63-65`、`101-103`、`128-130`）：

```python
# InMemoryTaskRepository
def list_all(self) -> list[Task]:
    with self._lock:
        return list(self._tasks.values())

# InMemoryResourceRepository
def list_all(self) -> list[Resource]:
    with self._lock:
        return list(self._resources.values())

# InMemoryDealRepository
def list_all(self) -> list[Deal]:
    with self._lock:
        return list(self._deals.values())
```

`list(...)` 构造新列表，外部修改不影响内部状态。

#### 3.2.3 Postgres 实现

PG 仓储用 SQLAlchemy `select(Model)` 取全量，再通过 converter 转换为领域对象（`postgres/task_repo.py:132-136`、`resource_repo.py:75-79`、`deal_repo.py:58-62`）：

```python
# PostgresTaskRepository
def list_all(self) -> list[Task]:
    with self._session() as session:
        stmt = select(TaskModel)
        models = session.execute(stmt).scalars().all()
        return [self._reconstruct_if_composite(session, m) for m in models]

# PostgresResourceRepository
def list_all(self) -> list[Resource]:
    with self._session() as session:
        stmt = select(ResourceModel)
        models = session.execute(stmt).scalars().all()
        return [resource_from_orm(m) for m in models]

# PostgresDealRepository
def list_all(self) -> list[Deal]:
    with self._session() as session:
        stmt = select(DealModel)
        models = session.execute(stmt).scalars().all()
        return [deal_from_orm(m) for m in models]
```

Task 仓储额外调用 `_reconstruct_if_composite` 重建复合任务的子任务与依赖关系。

#### 3.2.4 router 改造

三个 list 端点从 `getattr(repo, "_tasks", {})` 改为 `repo.list_all()`，过滤逻辑不变。以 `tasks.py:76-101` 为例：

`resources.py:95-123` 与 `deals.py:90-118` 同理，分别按 `domain_tag/status/supplier_id` 与 `task_id/supplier_id/status` 过滤。

#### 3.2.5 修复前后对比

| 模式 | 修复前（穿透私有属性） | 修复后（list_all） |

### 3.3 Lifespan 资源释放

`transport/app.py:56-72` 的 lifespan 在 shutdown 分支追加 `server.stop()` 与 `server.dispose()`：

```python
@asynccontextmanager
async def lifespan(app: FastAPI):
    # startup
    loop = asyncio.get_event_loop()
    ws_bridge_ref["loop"] = loop
    bridge = make_ws_event_bridge(ws_manager, loop)
    ws_bridge_ref["bridge"] = bridge
    server.event_bus.subscribe_all(bridge)
    logger.info("UMCP HTTP 服务已启动")
    yield
    # shutdown
    if ws_bridge_ref["bridge"]:
        server.event_bus.unsubscribe_all(ws_bridge_ref["bridge"])
    await ws_manager.disconnect_all()
    server.stop()
    server.dispose()
    logger.info("UMCP HTTP 服务已停止")
```

**安全性**：`server.dispose()` 内部有 `hasattr(self, "_postgres_bundle")` 守卫，in-memory 模式下未持有 PG bundle 时是 no-op；PG 模式下释放 SQLAlchemy engine 与连接池。

**shutdown 顺序**：

```
yield (请求处理结束)
  │
  ├─ 1. event_bus.unsubscribe_all(bridge)    ← 取消 WS 桥接订阅（需先于 disconnect_all）
  ├─ 2. ws_manager.disconnect_all()          ← 关闭所有 WS 连接
  ├─ 3. server.stop()                        ← 停止协议栈
  └─ 4. server.dispose()                     ← 释放 PG 连接池（in-memory 下 no-op）
```

### 3.4 WS 推送链路

#### 3.4.1 Task._emit payload 补全

`core/task.py:123-138` 的 `_emit` 在 payload 模板中补 `demander_id`：

```python
def _emit(self, event_type: EventType, payload: dict[str, Any] | None = None) -> None:
    if self._event_bus is None:
        return
    from umcp_core.events.bus import Event

    self._event_bus.publish(
        Event(
            type=event_type,
            source_layer="L2",
            payload={
                "task_id": self.task_id,
                "demander_id": self.demander_id,
                **(payload or {}),
            },
        )
    )
```

`assign_to`（`task.py:101-110`）在 payload 中传 `supplier_id`：

```python
def assign_to(self, resource_id: str) -> None:
    if self.status not in (TaskStatus.MATCHING, TaskStatus.PUBLISHED):
        raise RuntimeError(f"任务状态 {self.status} 不允许指派")
    self.assigned_resource_id = resource_id
    self._transition(TaskStatus.ASSIGNED)
    self._emit(
        EventType.TASK_ASSIGNED,
        payload={"supplier_id": resource_id},
    )
```

#### 3.4.3 router 绑定 event_bus

def unsubscribe_all(self, handler: EventHandler) -> None:
    """取消订阅全局事件（与 subscribe_all 配对）。"""
    with self._lock:

## 四、关键实现细节

### 4.1 logout 原本无效的修复

阶段五 B 的 logout 端点虽调用 `jwt_service.revoke(access_jti)`，但：

- access 与 refresh 的 jti 无关联，logout 无法吊销 refresh token
- 客户端仍可用 refresh token 调 `/refresh` 换取新 access token，登出形同虚设

修复方案是在 `JwtService.issue` 中嵌入 `refresh_jti`（`auth.py:47-60`），logout 端点据此一并吊销（`routers/auth.py:104-108`）。修复后 logout 让 access 与 refresh 同时进入黑名单，`/refresh` 端点的 `is_revoked` 校验会拒绝旧 refresh token。

### 4.2 refresh 端点 token 轮换

阶段五 B 的 refresh 端点用旧 refresh token 签发新对后，旧 refresh token 仍然有效，可被反复重放。修复方案是在签发新对之前 `jwt_service.revoke(old_jti)`（`routers/auth.py:77-79`），实现 token 轮换：每次 refresh 后旧 refresh 失效，客户端必须用新 refresh 继续轮换。

### 4.3 Deal.cancel/resolve 原本不发事件的修复

阶段五 C 初版（实现计划任务 10）只为 `activate/complete/open_dispute` 三个状态变更发事件，`cancel` 与 `resolve` 不发事件。这导致 `DEAL_CANCELLED`、`DEAL_RESOLVED` 两个枚举成员虽存在于 `WS_PUSHABLE_EVENTS` 白名单，却永不触发。

`core/deal.py:69-74` 与 `83-95` 在 `cancel` 与 `resolve` 中补发事件（见 3.4.2 表格），router 的 `cancel_deal`（`deals.py:191-207`）与 `resolve_deal`（`deals.py:210-227`）也绑定 event_bus。该补全在阶段五 D 完成。

### 4.4 EventType 缺失导致 WS_PUSHABLE_EVENTS 引用错误的修复

阶段五 B 在 `ws.py` 中把 `DEAL_CREATED`、`DEAL_PAID` 等加入 `WS_PUSHABLE_EVENTS`，但 `events/types.py` 尚未定义这些枚举成员，导致 `AttributeError`。阶段五 C 在 `events/types.py:41-50` 补全 `RESOURCE_REGISTERED`、`RESOURCE_STATUS_CHANGED` 与 6 个 `DEAL_*` 枚举，使白名单引用生效。

### 4.5 EventBus 缺少 unsubscribe_all 导致闭包泄漏的修复

阶段五 B 的 lifespan startup 调用 `event_bus.subscribe_all(bridge)` 注册 WS 桥接闭包，但 shutdown 时无对应取消方法，闭包滞留 `_global_handlers` 列表。多次启停应用会导致闭包累积，向已关闭的事件循环投递协程。

阶段五 C 在 `events/bus.py:74-78` 新增 `unsubscribe_all`，lifespan shutdown 调用 `event_bus.unsubscribe_all(ws_bridge_ref["bridge"])`（`app.py:67-68`）清理闭包。

### 4.6 PG 仓储 list_all 的复合任务重建

`PostgresTaskRepository.list_all`（`task_repo.py:132-136`）对每行模型调用 `_reconstruct_if_composite`，与 `find_by_id`、`find_by_demander`、`find_by_status` 共用同一重建逻辑，确保 list 端点返回的复合任务携带完整子任务与依赖关系。

### 4.7 router 状态变更端点的 event_bus 重绑定

从仓储取出的 Deal 实例（无论 in-memory 还是 PG）不持有 event_bus 引用——PG 反序列化时不注入，in-memory 虽存原对象但跨请求边界不应假设引用仍有效。因此 `activate_deal`、`complete_deal`、`dispute_deal`、`cancel_deal`、`resolve_deal` 五个端点都在 `find_by_id` 之后、状态变更之前调用 `deal.bind_event_bus(server.event_bus)`，保证事件能正确发布。
