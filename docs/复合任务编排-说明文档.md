# 复合任务编排（阶段四 C）说明文档

**阶段**：四 C（复合任务编排）
**适用范围**：`UMCPServer` 中跨 domain 子任务 DAG 编排、事件驱动状态转移与失败传播机制
**文档定位**：面向核心库使用者和插件开发者，完整说明 `CompositeTask` 的数据结构、DAG 校验、事件驱动状态机、`UMCPServer.execute_composite` 编排路由、关键实现坑点与使用方法。

---

## 一、概述

### 1.1 阶段目标

阶段四 C 的目标是让一个父任务（`CompositeTask`）可以包含跨多个 domain 的子任务，子任务通过 `depends_on` 声明 DAG 依赖，由现有 `EventBus` 驱动状态转移，失败按依赖传播。

三个核心能力：

1. **跨 domain 子任务 DAG 编排**：父任务持有 `subtasks` 与 `dependencies`，构造时即校验拓扑合法性（无环、无自环、引用存在），支持并行与串行混合
2. **事件驱动状态转移**：子任务 `COMPLETED`/`CANCELLED` 通过 `SUBTASK_*` 事件桥接触发父任务状态更新，不引入显式 Orchestrator
3. **失败按依赖传播**：失败子任务 → 下游取消，无依赖兄弟继续执行；父任务在任一子任务 `CANCELLED` 时 fail-fast 失败

**核心场景**：商务出行包 = 打车（ride 域）+ 代驾（escort 域）+ 团购伴手礼（group_buying 域）。代驾依赖打车先完成，团购与打车并行；父任务等所有子任务终态化后自动 `COMPLETED` 或 `CANCELLED`。

### 1.2 解决的问题

阶段四 A/B 完成后，`UMCPServer` 已支持多插件并存与跨域信任隔离，但任务模型仍是单 domain 的（`StandardTask` / `CustomTask` / `PackageTask`）。这带来两个限制：

- **跨业务组合无法表达**：商务出行包同时涉及 ride / escort / group_buying 三个 domain，现有 `PackageTask` 仅是同 domain 内"标准子任务 + 非标子任务"的容器，无法声明跨域依赖与执行顺序
- **缺乏编排与失败传播机制**：现有 `publish_and_match` 只能驱动单任务走完 `publish → assign → complete` 生命周期，无法按 DAG 拓扑序派发子任务，也无法在某个子任务失败时自动取消其下游

### 1.3 核心设计

阶段四 C 通过**新增 `CompositeTask` 子类 + 事件桥接**实现编排，核心库抽象基类零修改：

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 编排职责 | 事件驱动状态机 | 复用现有 `EventBus`，不引入显式 Orchestrator，与协议栈分层风格一致 |
| 执行模式 | DAG，子任务声明 `depends_on` | 支持并行与串行混合，拓扑由业务方声明 |
| 失败策略 | 按依赖传播失败 | 失败子任务 → 下游取消，无依赖兄弟继续；父任务 fail-fast |
| 父任务模型 | 新增 `CompositeTask` 继承 `PackageTask` | 复用现有抽象，`PackageTask` / `TenderTask` 平滑兼容 |
| 子任务执行 | 按 `domain_tag` 路由到对应插件 | 阶段四 A/B 已支持，子任务自治，零插件改动 |
| 事件桥接 | `EventBus` 订阅 `TASK_COMPLETED` 桥接到 `SUBTASK_*` | 不修改子任务类，父任务通过 `composite_task_id` 过滤事件 |
| 扩展点 | `register_subtask_executor` | 允许插件覆盖默认执行路径（如延迟完成、异步执行） |

设计要点：
1. `CompositeTask` 持有统一的 `subtasks` 列表与 `dependencies` 映射，构造时 fail-fast 校验 DAG
2. 父任务订阅 `SUBTASK_COMPLETED` / `SUBTASK_CANCELLED`，由事件驱动自身状态转移
3. `UMCPServer.execute_composite` 只负责"启动"（绑定总线、发布父任务、派发就绪子任务），"完成判定"完全由事件驱动
4. `TASK_COMPLETED` → `SUBTASK_*` 的桥接通过 `task_id ∈ subtask_ids` 过滤，避免全量扫描

### 3.2 CompositeTask 类结构

`CompositeTask` 继承 `PackageTask`（见 `task.py:200`），在父类基础上新增 `subtasks` 统一存储与 `dependencies` 依赖映射（`composite_task.py:13-32`）：

```python
class CompositeTask(PackageTask):
    def __init__(
        self,
        demander_id: str,
        domain_tag: DomainTag,                  # 父任务标识域，不参与子任务路由
        subtasks: list[Task] | None = None,
        dependencies: dict[str, list[str]] | None = None,
        **kwargs: Any,
    ) -> None:
        super().__init__(demander_id, domain_tag, **kwargs)
        self.subtasks: list[Task] = subtasks or []
        self.dependencies: dict[str, list[str]] = dependencies or {}
        self._sync_to_package_fields()          # 同步到 PackageTask 字段（向后兼容）
        self._validate_dag()                    # 构造时即拒绝非法拓扑
```

**字段说明**：

| 字段 | 类型 | 含义 |
|------|------|------|
| `subtasks` | `list[Task]` | 统一存储所有子任务（合并 standard + custom），便于 DAG 遍历 |
| `dependencies` | `dict[str, list[str]]` | 依赖映射：`subtask_id → [depends_on_subtask_id, ...]` |
| `standard_sub_tasks` | `list[StandardTask]` | 由 `_sync_to_package_fields` 同步，保持 `PackageTask` 访问路径兼容 |
| `custom_sub_task` | `CustomTask | None` | 同上，取第一个 `CustomTask` 子任务 |

`task_type()` 返回 `"composite"`（`composite_task.py:34-35`），与 `PackageTask` 的 `"package"` 区分。

### 3.3 DAG 构造与校验

DAG 校验在构造时 fail-fast 执行（`composite_task.py:70-96`），三项检查：

1. **引用存在**：依赖键与依赖目标都必须在 `subtasks` 列表中（`composite_task.py:73-78`）
2. **无自环**：子任务不能依赖自身（`composite_task.py:79-80`）
3. **无环检测**：三色 DFS，遇到 GRAY 节点即抛 `ValueError`（`composite_task.py:82-96`）

```python
def _validate_dag(self) -> None:
    sub_ids = {s.task_id for s in self.subtasks}
    for sub_id, deps in self.dependencies.items():
        if sub_id not in sub_ids:
            raise ValueError(f"依赖键 {sub_id} 不在子任务列表中")
        for d in deps:
            if d not in sub_ids:
                raise ValueError(f"依赖目标 {d} 不在子任务列表中")
            if d == sub_id:
                raise ValueError(f"子任务 {sub_id} 不能依赖自身")
    # 环检测（三色 DFS）
    WHITE, GRAY, BLACK = 0, 1, 2
    color = {sid: WHITE for sid in sub_ids}
    def dfs(node: str) -> None:
        color[node] = GRAY
        for dep in self.dependencies.get(node, []):
            if color[dep] == GRAY:
                raise ValueError(f"检测到环：{node} → {dep}")
            if color[dep] == WHITE:
                dfs(dep)
        color[node] = BLACK
    for sid in sub_ids:
        if color[sid] == WHITE:
            dfs(sid)
```

**DAG 查询接口**（供事件驱动状态转移使用）：

| 方法 | 位置 | 语义 |
|------|------|------|
| `ready_subtasks()` | `composite_task.py:39-48` | 返回依赖全部 `COMPLETED` 且自身 `DRAFT` 的子任务 |
| `pending_subtasks()` | `composite_task.py:50-52` | 返回非终态子任务 |
| `descendants(subtask_id)` | `composite_task.py:54-66` | BFS 返回直接或间接依赖 `subtask_id` 的所有下游 ID（用于失败传播） |
| `_build_reverse_deps()` | `composite_task.py:110-115` | 构造反向邻接表，供 `descendants` 遍历 |

### 3.4 事件驱动状态转移机制

#### 3.4.1 事件类型扩展

`EventType` 新增四个事件类型（`types.py:52-56`）：

```python
# 复合任务编排（阶段四C）
SUBTASK_COMPLETED = "subtask.completed"      # 子任务完成
SUBTASK_CANCELLED = "subtask.cancelled"      # 子任务取消
COMPOSITE_COMPLETED = "composite.completed"  # 复合任务整体完成
COMPOSITE_FAILED = "composite.failed"        # 复合任务整体失败
```

**为什么需要 `SUBTASK_*` 事件**：现有 `TASK_COMPLETED` 的 payload 只含 `task_id`，无法快速区分是否属于某复合任务的子任务。`SUBTASK_*` 事件携带 `composite_task_id`，父任务回调通过该字段过滤，避免全量扫描。

#### 3.4.2 SUBTASK_* 事件桥接

`CompositeTask` 不直接订阅 `TASK_COMPLETED`（子任务事件），而是由 `UMCPServer.execute_composite` 注册桥接函数（`server.py:430-443`）将 `TASK_COMPLETED` 转换为 `SUBTASK_*`：

```python
def _bridge_to_subtask_event(event: Event) -> None:
    task_id = event.payload.get("task_id")
    if task_id not in subtask_ids:               # 过滤非本复合任务的子任务
        return
    subtask = composite._find_sub(task_id)
    if event.payload.get("cancelled"):           # cancel() 携带 cancelled=True
        composite.emit_subtask_event(subtask, EventType.SUBTASK_CANCELLED)
    else:
        composite.emit_subtask_event(subtask, EventType.SUBTASK_COMPLETED)
    self._dispatch_ready_subtasks(composite)     # 推进串行依赖链
    if TaskStatus.is_terminal(composite.status): # 终态后取消订阅
        self.event_bus.unsubscribe(EventType.TASK_COMPLETED, _bridge_to_subtask_event)
```

**桥接关键点**：
- 通过 `task_id ∈ subtask_ids` 过滤，多个复合任务共享同一 `EventBus` 时互不干扰
- 通过 `payload["cancelled"]` 区分完成/取消（`Task.cancel()` 在 `task.py:94` 携带 `cancelled=True`）
- 桥接后立即调用 `_dispatch_ready_subtasks` 推进新就绪的子任务（串行依赖链推进）

#### 3.4.3 CompositeTask 事件回调

`CompositeTask.bind_event_bus` 订阅 `SUBTASK_COMPLETED` / `SUBTASK_CANCELLED`（`composite_task.py:125-129`）：

```python
def bind_event_bus(self, bus: EventBus) -> None:
    super().bind_event_bus(bus)
    bus.subscribe(EventType.SUBTASK_COMPLETED, self._on_subtask_completed)
    bus.subscribe(EventType.SUBTASK_CANCELLED, self._on_subtask_cancelled)
```

`_on_subtask_completed`（`composite_task.py:150-160`）的状态转移逻辑：

```python
def _on_subtask_completed(self, event: Event) -> None:
    if event.payload.get("composite_task_id") != self.task_id:
        return
    # 任一子任务被取消 → 父任务立即失败（fail-fast，无需等待所有子任务终态化）
    if any(s.status == TaskStatus.CANCELLED for s in self.subtasks):
        self._fail_composite()
        return
    if any(not TaskStatus.is_terminal(s.status) for s in self.subtasks):
        return
    self._complete_composite()
```

**关键顺序**：先检查 CANCELLED 再检查终态化。原规格先检查"所有终态"再检查"有 CANCELLED"，导致子任务取消后必须等待所有子任务终态化才 fail 父任务，不符合 fail-fast（详见 4.1）。

### 3.5 失败传播策略

`_on_subtask_cancelled`（`composite_task.py:162-173`）负责传播取消到下游：

```python
def _on_subtask_cancelled(self, event: Event) -> None:
    if event.payload.get("composite_task_id") != self.task_id:
        return
    failed_id = event.payload.get("subtask_id")
    downstream_ids = self.descendants(failed_id)        # 仅下游，兄弟无依赖不受影响
    for sub_id in downstream_ids:
        sub = self._find_sub(sub_id)
        if not TaskStatus.is_terminal(sub.status):
            sub.cancel()
            self.emit_subtask_event(sub, EventType.SUBTASK_CANCELLED)  # 递归传播
    self._on_subtask_completed(event)                   # 复用完成判定逻辑
```

**传播规则**：

| 子任务关系 | 失败时的处理 | 原因 |
|-----------|-------------|------|
| 下游（直接或间接依赖失败子任务） | `cancel()` 并递归 emit `SUBTASK_CANCELLED` | 依赖无法满足，必须取消 |
| 无依赖兄弟 | 不受影响，继续执行 | 无依赖关系，可独立完成 |
| 父任务 | 任一子任务 `CANCELLED` 即 fail-fast `_fail_composite` | 复合任务整体失败 |

`descendants()` 仅返回下游（通过反向邻接表 BFS），保证兄弟任务不被误取消。父任务通过 `_on_subtask_cancelled` 末尾调用 `_on_subtask_completed` 复用 fail-fast 判定。

### 3.6 UMCPServer.execute_composite 编排路由

`execute_composite`（`server.py:398-448`）是编排入口，只负责"启动"，不负责"完成判定"：

```python
def execute_composite(self, composite: CompositeTask) -> None:
    if not isinstance(composite, CompositeTask):
        raise TypeError(f"期望 CompositeTask，收到 {type(composite).__name__}")
    if composite.status != TaskStatus.DRAFT:
        raise RuntimeError(f"复合任务状态 {composite.status} 不允许执行")

    self._persist_composite_atomic(composite)          # 0. 原子持久化父+子任务
    composite.bind_event_bus(self.event_bus)            # 1. 订阅子任务事件
    composite.publish()                                 # 2. DRAFT → MATCHING

    subtask_ids = {s.task_id for s in composite.subtasks}
    def _bridge_to_subtask_event(event: Event) -> None:
        ...                                             # 3. 注册桥接（见 3.4.2）
    self.event_bus.subscribe(EventType.TASK_COMPLETED, _bridge_to_subtask_event)

    self._dispatch_ready_subtasks(composite)            # 4. 启动就绪子任务
```

**编排路由入口**：`publish_and_match`（`server.py:450-489`）在收到 `CompositeTask` 时委托 `execute_composite`（`server.py:465-467`），对外提供统一任务发布入口。

**子任务派发**：`_dispatch_ready_subtasks`（`server.py:491-504`）遍历 `ready_subtasks()`，按 domain 路由执行：

```python
def _dispatch_ready_subtasks(self, composite: CompositeTask) -> None:
    for subtask in composite.ready_subtasks():
        if subtask.status != TaskStatus.DRAFT:
            continue                                    # DRAFT 状态守卫（见 4.3）
        subtask.bind_event_bus(self.event_bus)
        self._execute_subtask_by_domain(subtask)
```

`_execute_subtask_by_domain`（`server.py:506-531`）按 `domain_tag` 路由，优先使用注册的自定义执行器，否则走默认执行器（`publish → assign → start_execution → complete`）：

```python
def _execute_subtask_by_domain(self, subtask: Task) -> None:
    domain = subtask.domain_tag.value
    custom_executor = self._subtask_executors.get(domain)
    if custom_executor is not None:
        custom_executor(subtask)                        # 自定义执行器自行控制 publish 时机
        return
    strategy = self.match_strategy_for(domain)          # 阶段四A 的 domain 路由
    ...
    subtask.publish()                                   # 默认执行器负责 publish
    candidates = self.resource_repo.find_available(subtask.domain_tag)
    result = strategy.execute(subtask, candidates)
    if not result.matched:
        subtask.cancel()                                # 无匹配 → 取消 → 触发失败传播
        return
    subtask.assign_to(result.selected_resource_id)
    subtask.start_execution()
    subtask.complete()
```

## 四、关键实现细节（含已修复的坑）

### 4.1 `_on_subtask_completed` 顺序问题：先检查 CANCELLED 再检查终态化

**问题**：原规格先检查"所有子任务终态化"再检查"有 CANCELLED"，导致子任务取消后必须等待所有子任务终态化才 fail 父任务，不符合 fail-fast 语义。在失败传播场景下，下游子任务被递归取消时，若存在尚未终态化的无依赖兄弟，父任务会一直停留在非终态。

**修复**（`composite_task.py:150-160`）：调换顺序——任一子任务 `CANCELLED` 立即 `_fail_composite` 返回；否则检查全部终态化才 `_complete_composite`：

```python
def _on_subtask_completed(self, event: Event) -> None:
    if event.payload.get("composite_task_id") != self.task_id:
        return
    if any(s.status == TaskStatus.CANCELLED for s in self.subtasks):  # 先检查 CANCELLED
        self._fail_composite()
        return
    if any(not TaskStatus.is_terminal(s.status) for s in self.subtasks):  # 再检查终态化
        return
    self._complete_composite()
```

### 4.2 `_complete_composite` 绕过状态机校验

**问题**：`execute_composite` 中 `composite.publish()` 已将父任务推进到 `MATCHING`（`server.py:425`）。若 `_complete_composite` 调用 `Task.complete(self)`，`Task._transition`（`task.py:116-121`）会经 `TaskStateMachine` 校验 `MATCHING → COMPLETED` 转移，而状态机不允许该直接转移（必须经 `ASSIGNED → IN_PROGRESS → COMPLETED`），抛 `RuntimeError`。此外 `PackageTask.complete` 还会校验子任务，与 `CompositeTask` 事件驱动的一致性保证冲突。

**修复**（`composite_task.py:175-194`）：直接设置终态字段，跳过 `Task.complete` 的状态机校验与 `PackageTask.complete` 的子任务校验。`CompositeTask` 由事件驱动保证一致性，无需重复校验：

```python
def _complete_composite(self) -> None:
    if self.status == TaskStatus.COMPLETED:
        return
    self.status = TaskStatus.COMPLETED                # 直接设置，绕过 _transition
    from datetime import datetime
    self.updated_at = datetime.utcnow()
    if self._event_bus:
        ...emit COMPOSITE_COMPLETED
```

`_fail_composite`（`composite_task.py:196-216`）调用 `self.cancel()`，此时父任务处于 `MATCHING`（非终态），`Task.cancel` 的状态机校验可正常通过。

### 4.3 EventBus 同步重入与 DRAFT 状态守卫

**问题**：`EventBus.publish` 是同步执行（`bus.py:49-62`，复制 handlers 列表后逐个 `handler(event)`）。`_execute_subtask_by_domain` 默认执行器中 `subtask.complete()` 会同步 emit `TASK_COMPLETED` → 触发桥接 → emit `SUBTASK_COMPLETED` → 触发 `_on_subtask_completed` → 桥接回调中调用 `_dispatch_ready_subtasks` 派发新就绪子任务。递归返回后，原始 `_dispatch_ready_subtasks` 循环继续迭代 `ready_subtasks()` 返回的列表，但其中部分子任务可能已被递归派发推进（不再是 `DRAFT`），导致重复 publish 或非法状态转移。

**修复**（`server.py:500-504`）：派发前重新校验 `DRAFT` 状态，跳过已被递归推进的子任务：

```python
def _dispatch_ready_subtasks(self, composite: CompositeTask) -> None:
    for subtask in composite.ready_subtasks():
        if subtask.status != TaskStatus.DRAFT:
            continue  # 可能在递归派发中已被推进
        subtask.bind_event_bus(self.event_bus)
        self._execute_subtask_by_domain(subtask)
```

**publish 时机调整**：`_dispatch_ready_subtasks` 仅 `bind_event_bus`，`publish` 交给 `_execute_subtask_by_domain` 默认分支（`server.py:522`）或自定义执行器。原因：默认执行器需要 `DRAFT → publish → MATCHING → assign_to` 的合法路径；自定义执行器期望子任务进入时是 `DRAFT`，自行控制 publish 时机，避免双重 publish。

### 4.4 闭包订阅泄漏与终态 unsubscribe

**问题**：每次 `execute_composite` 注册闭包 `_bridge_to_subtask_event`（捕获 `composite` 与 `subtask_ids`）但从不取消订阅。复合任务到达终态后，闭包仍持有 `composite` 强引用，导致内存泄漏；且后续无关的 `TASK_COMPLETED` 事件仍会触发闭包执行（虽被 `task_id ∈ subtask_ids` 过滤，但仍有开销）。

**修复**（`server.py:441-443`）：桥接函数在每次执行末尾检查复合任务是否终态，终态则 `unsubscribe`：

```python
def _bridge_to_subtask_event(event: Event) -> None:
    ...
    self._dispatch_ready_subtasks(composite)
    if TaskStatus.is_terminal(composite.status):
        self.event_bus.unsubscribe(EventType.TASK_COMPLETED, _bridge_to_subtask_event)
```

**安全性**：`EventBus.publish` 在调用前复制 handlers 列表（`bus.py:53`，`handlers = list(...)`），handler 内部 `unsubscribe` 不会影响当前迭代，不会抛 `RuntimeError`。

该修复由 `test_bridge_unsubscribed_after_composite_terminal` 与 `test_bridge_unsubscribed_after_composite_failed`（`test_composite_orchestration.py:176,197`）验证，通过 `handler_count` 断言订阅前后数量一致。

## 五、使用方法

### 5.1 构造 DAG 与启动编排

```python
from umcp_core.core.composite_task import CompositeTask
from umcp_core.core.domain import DomainTag
from umcp_core.core.task import StandardTask
from umcp_core.server import UMCPServer

server = UMCPServer()
server.use_in_memory_repositories()

# 为三个 domain 注册匹配策略与资源（见阶段四A 文档）
server.register_match_strategy("ride", ride_strategy)
server.register_match_strategy("escort", escort_strategy)
server.register_match_strategy("group_buying", gb_strategy)
# ... server.resource_repo.save(...) 注册资源

# 构造子任务
sub_ride = StandardTask(demander_id="u1", domain_tag=DomainTag.of("ride"), title="打车去机场")
sub_ride.task_id = "ride_1"
sub_escort = StandardTask(demander_id="u1", domain_tag=DomainTag.of("escort"), title="代驾回家")
sub_escort.task_id = "escort_1"
sub_gb = StandardTask(demander_id="u1", domain_tag=DomainTag.of("group_buying"), title="团购伴手礼")
sub_gb.task_id = "gb_1"

# 构造 CompositeTask：代驾依赖打车，团购与打车并行
composite = CompositeTask(
    demander_id="u1",
    domain_tag=DomainTag.of("composite"),       # 父任务标识域，不参与子任务路由
    subtasks=[sub_ride, sub_escort, sub_gb],
    dependencies={"escort_1": ["ride_1"]},      # 代驾 depends_on 打车
)

# 启动编排（execute_composite 只负责启动，完成判定由事件驱动）
server.execute_composite(composite)
# 或通过统一入口：server.publish_and_match(composite)
```

## 七、已知限制与性能考量

### 7.1 已知限制

| 限制 | 说明 | 后续方向 |
|------|------|---------|
| 跨域资源 | 一个资源不能同时属于多个 domain | 后续阶段支持多域资源 |
| 子任务间数据传递 | 当前仅状态依赖，前一个子任务的输出无法作为后一个的输入 | 后续支持数据流编排 |
| 子任务超时自动取消 | 当前无超时机制 | 后续增加 `timeout` 字段与定时器 |
| 复合任务进度查询索引 API | 需遍历 `subtasks` 状态实现 | 后续提供聚合查询接口 |

### 7.2 性能考量

| 项 | 风险 | 建议阈值 / 优化方向 |
|----|------|---------------------|
| **DAG 链长度** | `EventBus` 同步 `publish` 导致串行依赖链 A→B→C→...→N 的调用栈深度 = 链长度。Python 默认递归上限 1000，长依赖链可能 `RecursionError` | **建议链长度 < 100**。如需支持深度 DAG，应改为迭代式派发（事件入队后异步消费） |
| **cancel 传播事件复杂度** | `_on_subtask_cancelled` 中每个被传播取消的下游子任务都会触发完整事件链路（cancel → 桥接 → `SUBTASK_CANCELLED` → `_on_subtask_cancelled` → `descendants()` O(V+E) 遍历）。密集 DAG 总事件数可达 **O(n²)** | 不会导致错误状态（终态守卫正确），但效率低下。如需优化可改为批量取消并合并事件 |
| **同步 EventBus 栈溢出风险** | `EventBus.publish` 同步执行（`bus.py:49-62`），深层 DAG + 密集事件会累积调用栈 | 与 DAG 链长度限制同源，建议链长度 < 100；生产环境可替换为异步 `EventBus` 实现（Kafka/Pulsar） |
| **`_find_sub` 线性查找** | `_find_sub`（`composite_task.py:100-104`）按 `task_id` 线性遍历 `subtasks`，单次 O(n) | 子任务规模通常较小（< 50），可接受；超大 DAG 可维护 `task_id → Task` 索引 |
| **`descendants` 重复构造反向邻接表** | 每次调用 `_build_reverse_deps`（`composite_task.py:110-115`）重新构造 | 失败传播场景下调用频率低，可接受；高频场景可缓存 |
